# Начни отсюда: как разобраться в проекте за 5 этапов

Этот кейс нужен не для того, чтобы произносить красивые слова, а чтобы **понимать, что ты сделала и зачем**.

## Этап 1. Пойми бизнес-задачу (без кода)

Представь приложение доставки еды. Люди регистрируются, выбирают адрес, смотрят ресторан, кладут блюдо в корзину, начинают оформление и оплачивают. Бизнес хочет, чтобы больше новых пользователей дошли до **первого оплаченного заказа**.

**Главный вопрос:** на каком переходе теряем больше всего людей? **Второй:** есть ли заметные проблемы в конкретных сегментах?

## Этап 2. Научись читать одну строку данных

В `data/sample/users_sample.csv` у каждого пользователя указаны ID, дата регистрации, платформа и канал. В `data/sample/events_sample.csv` у него может быть несколько строк событий, каждое — действие в приложении. Одна строка событий **не равна одному пользователю**.

Открой `docs/data_dictionary.md`: выучи шесть основных событий. Попробуй вручную найти пользователя, который дошёл до `checkout_started`, но не оставил `order_completed`.

## Этап 3. Выучи три формулы

1. **Общая конверсия** = пользователи с первым заказом / все зарегистрированные × 100%.
2. **Конверсия между двумя соседними этапами** = пользователи следующего этапа / пользователи предыдущего × 100%.
3. **Потеря на этапе** = пользователи предыдущего этапа − пользователи следующего.

Числа для перепроверки: **3 974 / 12 000 = 33,1%**. От просмотра ресторана до корзины не дошло **8 922 − 6 316 = 2 606** пользователей.

## Этап 4. Открой код постепенно

1. `sql/02_funnel_overall.sql` — сначала разберись, как SQL считает людей по шагам.
2. `sql/03_funnel_by_segment.sql` — как сравниваем платформы и каналы.
3. `sql/04_payment_failures.sql` — как мы выявили различия в событиях ошибок оплаты.
4. `scripts/run_analysis.py` — как Python выполняет SQL и строит графики.
5. `scripts/generate_data.py` — откуда взялись синтетические пользователи и почему Android и iOS разные.

Не пытайся заучить всё сразу. Важно самостоятельно объяснить смысл запросов, что хранится в каждой таблице и почему берём **уникального пользователя**, а не количество действий.

## Этап 5. Запусти своими руками

На Mac или Linux, в терминале внутри папки проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m scripts.run_all
python -m pytest -q
```

На Windows в PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m scripts.run_all
python -m pytest -q
```

Если Windows не разрешает запуск скрипта активации, можно обойти это командами `.venv\Scripts\python.exe -m pip install -r requirements.txt` и `.venv\Scripts\python.exe -m scripts.run_all` без активации.

После запуска открой `reports/analysis_report.md` и `INTERVIEW_GUIDE.md`.

## Небольшая самостоятельная работа

1. Объясни без подсказок, чем **33,1%** отличается от **71,7%** на последнем шаге.
2. Почему нельзя сказать «Android платит хуже именно из-за ошибки»?
3. Почему 2 606 потерянных на шаге «ресторан → корзина» **не** означает, что именно его стоит чинить первым?
4. Поменяй в `scripts/generate_data.py` для Android `0.33` на `0.20` в вероятности `payment_failed`, снова запусти проект и объясни, почему результат изменился. Это **эксперимент с генератором**, а не A/B-тест продукта.

Если уверенно решаешь эти четыре пункта — ты уже понимаешь основу кейса.
