# Воронка первого заказа в сервисе доставки еды

![Python](https://img.shields.io/badge/Python-pandas-blue) ![SQL](https://img.shields.io/badge/SQL-SQLite-lightgrey) ![Data](https://img.shields.io/badge/Data-synthetic-orange)

**Задача:** найти, на каких этапах новые пользователи не доходят до первого заказа, проверить отличия платформ и предложить измеримые продуктовые действия.

> **Важно:** это учебный проект на **полностью синтетических данных** (12 000 пользователей). Данные генерируются открытым кодом, не относятся к реальному бизнесу и намеренно моделируют различия между платформами. Результаты нельзя выдавать за рыночные закономерности или реальный эффект улучшения.

## Короткий ответ (чтобы не заставлять рекрутера читать весь код)

- **Первый заказ за 7 дней** сделали **3 974 из 12 000 пользователей (33,1%)**.
- **Крупнейшая потеря в абсолютных числах** — переход от просмотра ресторана к добавлению блюда в корзину: **2 606 пользователей**.
- **Дополнительная диагностическая точка** — checkout на Android: его завершает **66,2%**, тогда как на iOS — **77,9%**.
- Событие `payment_failed` встречается у **33,1% Android** и **12,4% iOS** пользователей, дошедших до checkout. Это основание **выдвинуть гипотезу** о трении в оплате, но не доказательство причины.
- **Следующий шаг продукта:** проверить качество логов, собрать детализацию ошибок и протестировать решение на Android через A/B-тест.

## Что я анализирую

| Вопрос | Метод |
|---|---|
| Сколько пользователей дошли до первого заказа? | Воронка, SQL, уникальный `user_id` |
| Где самые большие потери? | Step conversion, drop-off |
| Различаются ли платформы и каналы? | Сегментный анализ |
| Почему стоит изучить Android checkout? | Частота `payment_failed` и конверсия checkout |
| Возвращаются ли пользователи за новым заказом? | Repeat purchase в течение 7 и 30 дней |
| Что делать дальше? | Гипотеза, план сбора данных, A/B-тест |

## Технологии

- **SQL / SQLite:** CTE, подзапросы, `GROUP BY`, оконные функции `LAG`/`FIRST_VALUE`, проверка качества данных.
- **Python:** генерация событий, `pandas` для проверки расчётов, `matplotlib` для графиков.
- **Тесты:** `pytest` и проверки воспроизводимости; GitHub Actions запускает проект и тесты при коммитах.

## Как запустить и воспроизвести результат

Требуется **Python 3.10+**. Из корня проекта:

```bash
python -m pip install -r requirements.txt
python -m scripts.run_all
python -m pytest -q
```

Команда создаст локальные CSV в `data/raw/` (они не загружаются на GitHub) и заново сформирует отчёт, таблицы и графики. Генератор использует постоянный `seed = 20261029`, поэтому результаты повторяются.

## Методика и честные ограничения

- Период регистрации: январь — март 2026; окно наблюдения до 15 мая 2026 (UTC).
- Единица анализа — пользователь. Регистрация → адрес → ресторан → корзина → checkout → первый заказ; шаг засчитывается только **после предыдущего** и **не позднее 7 дней после регистрации**.
- Для repeat purchase знаменатель — пользователи с первым заказом, а не все регистрации. Доля за 7/30 дней **кумулятивная** (не exact-day retention).
- Сегментное сравнение **не показывает причину различия**. Android и iOS могут отличаться составом пользователей и условиями оплаты. В симуляции различия заданы механизмом генерации; в реальной компании потребовались бы дополнительные события и эксперимент.
- **Это не проведённый A/B-тест**: проект только предлагает план его проведения.

## Результат и следующий шаг

Я выделила две разные точки: наибольший **объём потерянных пользователей** находится между рестораном и корзиной, а **конкретная диагностическая гипотеза** — на этапе оплаты Android. Приоритет нельзя определять только по величине потерь: нужно учесть причину, ожидаемый эффект и стоимость исправления.

Для Android предлагаю проверить точность логирования ошибок, добавить разрезы по методам оплаты и версиям приложения и только после этого тестировать изменение. Подробно: [отчёт](reports/analysis_report.md).
